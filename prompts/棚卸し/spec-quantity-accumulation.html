棚卸し機能 — 同一商品スキャン時の数量加算

作成日: 2026-05-30 ｜ プロジェクト: sakemaru-handy-denso ｜ 対象: InventoryCount機能

1. 背景・目的

棚卸し作業では、同一商品が倉庫内の複数箇所に存在するため、同じJANコードを複数回スキャンして数量を積み上げる運用が発生する。現状は再スキャン時に前回の入力値が上書きされるため、ユーザーが手動で合計を計算して入力し直す必要がある。

本変更により、同一商品の再スキャン時に入力した数量が既存値に自動加算されるようにする。

2. 現状と変更後のフロー比較

現状（上書き）

  1. 商品Aスキャン → 空欄 → バラ5入力 → 確定
  2. 商品Aスキャン → 空欄 → バラ3入力 → 確定
  3. 結果: バラ3（5が消える）

変更後（加算）

  1. 商品Aスキャン → 空欄 → バラ5入力 → 確定
  2. 商品Aスキャン → 空欄 → バラ3入力 → 確定
  3. 結果: バラ8（5+3）
変更後のフロー:
JANスキャン → 商品特定 → 入力画面（空欄） → 数量入力 → 確定（既存値に加算） → dirtyInputsに累計保存 → キャッシュ → 一括送信

3. UI仕様

項目 仕様
入力フィールド 再スキャン時も常に空欄。ユーザーは増分のみ入力する。
既存数量の表示 なし（加算は裏側で自動処理）
合計バラ表示 入力中にリアルタイムで累計値（既存+入力中）を表示
確定メッセージ 「○○ の入力を保存しました（総バラ: X）」— Xは累計値

4. 設計: accumulatedBase アプローチ

Stateに一時的な「ベース値」を保持し、保存時にベース＋入力値を合計する方式。

4.1 概要

  • スキャンで商品が確定した時、既存のdirtyInputがあればそれを accumulatedBase にコピー
  • saveLocalInput() で保存する際、base.caseQty + 入力caseQty を計算して保存
  • UIフィールドは常に空欄（ユーザーは増分だけ入力）
  • accumulatedBase は非永続（キャッシュ不要）。アプリ再起動時はdirtyInputsから復元される

4.2 データフロー図

スキャン時:
  dirtyInputs[itemId] が存在する？
    ├─ YES → accumulatedBase = dirtyInputs[itemId] のコピー
    └─ NO  → accumulatedBase = null

保存時 (saveLocalInput):
  caseQty  = 入力ケース + (accumulatedBase?.caseQuantity ?: 0)
  pieceQty = 入力バラ   + (accumulatedBase?.pieceQuantity ?: 0)
  dirtyInputs[itemId] = LocalInventoryInput(caseQty, pieceQty, ...)

確定/クリア時:
  accumulatedBase = null

6. 各メソッドの変更詳細

6.1 InventoryCountState — フィールド追加

data class InventoryCountState(
    ...
    val accumulatedBase: LocalInventoryInput? = null,  // NEW
    val dirtyInputs: Map<Int, LocalInventoryInput> = emptyMap(),
    ...
) {
    val totalPieces: Int = run {
        val incCase  = caseQuantity.toIntOrNull() ?: 0
        val incPiece = pieceQuantity.toIntOrNull() ?: 0
        val baseCase  = accumulatedBase?.caseQuantity ?: 0
        val basePiece = accumulatedBase?.pieceQuantity ?: 0
        (incCase + baseCase) * capacityCase + (incPiece + basePiece)
    }
}

6.2 saveLocalInput() — 核心の変更

private fun saveLocalInput() {
    val current = _state.value
    val item = current.selectedItem ?: return
    if (current.caseQuantity.isBlank() && current.pieceQuantity.isBlank()) return

    val incrementCase  = current.caseQuantity.toIntOrNull() ?: 0
    val incrementPiece = current.pieceQuantity.toIntOrNull() ?: 0

    // 加算: Base値 + 入力値
    val base = current.accumulatedBase
    val caseQty  = incrementCase  + (base?.caseQuantity ?: 0)
    val pieceQty = incrementPiece + (base?.pieceQuantity ?: 0)

    val total = (caseQty * item.capacityCase.coerceAtLeast(1)) + pieceQty
    val input = LocalInventoryInput(
        itemId = item.id, itemCode = item.itemCode,
        itemName = item.itemName,
        locationNo = item.location?.locationNo,
        countRound = current.countRound,
        caseQuantity = caseQty, pieceQuantity = pieceQty,
        totalPieces = total
    )
    _state.update { it.copy(dirtyInputs = it.dirtyInputs + (item.id to input)) }
    persistCache()
}

6.3 scan() → applyResult()

fun applyResult(results: List<InventoryCountItemResponse>, quantityType: String?) {
    val singleItem = if (results.size == 1) results.first() else null
    val existingInput = singleItem?.let { _state.value.dirtyInputs[it.id] }
    _state.update {
        it.copy(
            items = results,
            selectedItem = singleItem,
            accumulatedBase = existingInput,  // NEW
            scanQuantityType = quantityType,
            scannedCode = raw, isItfCode = isItf,
            caseQuantity = "", pieceQuantity = "",
            keyword = "",
            error = if (results.size > 1) "複数の商品が見つかりました。選択してください" else null,
            message = null
        )
    }
}

6.4 selectItem()

fun selectItem(item: InventoryCountItemResponse) {

    _state.update {

}

# シナリオ 期待結果 保証メカニズム
1 A入力5確定 → A再スキャン → 入力3確定 合計 8 base=5, inc=3 → saveLocalInput: 5+3=8
2 A(既存5)スキャン → 何も入力せず → Bスキャン Aの値5は保持 空欄ガードでsaveLocalInput未実行。dirtyInputs[A]不変

5 アプリ再起動後に同一商品スキャン 前回の累計値に加算 dirtyInputsはキャッシュ復元済。スキャン時にbase化
6 3回連続スキャン: 5 → 3 → 2 合計 10 1回目: 0+5=5, 2回目: 5+3=8, 3回目: 8+2=10
7 finishRound送信 累計値がサーバーに送信 dirtyInputsに累計値が保存済。送信ロジック変更なし

8. テスト手順

  1. ビルド・起動 → 棚卸し画面へ遷移
  2. 商品Aスキャン → バラ5入力 → 確定 → メッセージ「総バラ: 5」を確認
  3. 同じ商品A再スキャン → フィールドが空欄であること確認 → バラ3入力 → 確定 → メッセージ「総バラ: 8」を確認
  4. 商品A再スキャン → 何も入力せず商品Bスキャン → Aのdirtyが8のまま保持されていること
  5. 商品A再スキャン → バラ2入力 → 確定せずアプリを閉じる → 再起動 → 商品Aスキャン → 確定時に前回までの累計が維持されていること
  6. finishRoundで送信 → サーバーに累計値が送られること

10.4 Android側の実装注意

  • スキャンしたコードは LocalInventoryInput または送信用DTOに保持し、同期時に search_code として送る。
  • ケースJANの場合、画面表示・ローカル計算ではそのコードの q を capacityCase として扱う。
  • バラJANの場合は q = 1 として扱う。
  • Androidモデルは t を 0=PIECE、1=CASE、2=CARTON に復元して扱う。
  • 同一商品の再スキャン時はAndroid側でも加算し、サーバ側でも加算される。同期時に送る値は「今回同期する増分」ではなく、Android内で保持している未送信累計値とする。
  • 同期成功後は送信済みのdirtyInputsのみクリアする。同期失敗時はローカル保存を残す。

11. Android側 追加仕様（2026-05-30追加）

11.1 ケースJAN対応

JAN辞書の q（入数）をケース入力時の総バラ数計算に使用する。

スキャンしたコード JAN辞書の q ケース2・バラ3を入力した場合の総バラ数
バラJAN（t=0, q=1） 1 2 × capacityCase（商品マスタ値） + 3
ケースJAN（t=1, q=6） 6 2 × 6 + 3 = 15
ケースJAN（t=1, q=20） 20 2 × 20 + 3 = 43
ルール: スキャンしたコードに q がある場合、ローカルでの総バラ数計算はその q を capacityCase の代わりに使う。送信時も search_code としてスキャンコードを添付し、サーバ側でも同じ q で変換される。

11.4.1 SoundUtils 追加メソッド

// SoundUtils.kt に追加

fun playSuccess() {
    try {
        if (toneGenerator == null) {
            toneGenerator = ToneGenerator(AudioManager.STREAM_SYSTEM, 100)
        }
        toneGenerator?.startTone(ToneGenerator.TONE_PROP_BEEP2, 150)
    } catch (e: Exception) {}
}

fun playError() {
    try {
        if (toneGenerator == null) {
            toneGenerator = ToneGenerator(AudioManager.STREAM_SYSTEM, 100)
        }
        toneGenerator?.startTone(ToneGenerator.TONE_PROP_NACK, 200)
    } catch (e: Exception) {}
}

12. WMS棚卸確定時の実棚変更反映ルール

項目 仕様
items.is_managed_stock = 0 WMS棚卸由来の実棚変更ではスキップしない。棚卸で確定した数量を real_stocks / real_stock_lots に反映する。
通常の手動実棚変更 従来通り is_managed_stock = 0 は対象外。今回の例外は source_type = WMS_INVENTORY_COUNT のみ。
差分数量 stock_quantity_after - 現在のreal_stocks.current_quantity を最終的な反映差分として扱う。
テスト確認 ローカル棚卸 id=8 の is_managed_stock = 0 明細で、実棚変更明細作成と real_stocks.current_quantity 更新を確認済み。

13. 懸念点と渋滞対策

箇所 確認結果・対策
棚卸対象の算出 棚卸対象は real_stocks.warehouse_id と current_quantity != 0 を基準に作成する。ローカル倉庫91では real_stocks 約3714件、active lot 約9573件。複数lotを持つ real_stock は多いが、複数ロケーションに分かれるものは9件。現状は real_stock 単位で1明細化し、最新active lotの棚番を代表表示するため、棚番別精度が必要な場合はlot/ロケーション単位明細への変更が次の改善点。
システム在庫0の商品 現状の棚卸対象は current_quantity != 0 のため、理論在庫0だが現物がある商品は初期データに含まれない。Handyのローカル検索も棚卸対象内だけを見るため、このケースは「対象外商品の発見」として別途追加明細を作るAPI/画面が必要。棚卸精度の観点では残課題。
JAN・入数連携 商品に紐づく active な item_search_information は全件連携する。ローカル棚卸 id=8 では3736商品のうち3730商品にactive検索コードあり。ケースJAN 4872件のうち3件は item_quantity_information.quantity が未設定または0のため、サーバ側はfallbackで1扱いになる。該当データはマスタ修正対象。
Handyの総バラ計算 スキャンしたJANコードと入数 q をローカル入力に保持し、同じ商品を再スキャンした場合はローカル未送信の総バラ数へ加算する。数字入力中の onValueChange は同じ入力欄の現在値で再計算し、入力途中の保存で二重加算しない。送信時は総バラ数を quantity、スキャンコードを search_code としてWMSへ送る。
初期同期データ量 items は500件ページング、JAN辞書は短縮キー形式。ローカル棚卸 id=8 の実測では items?page=1&per_page=500&compact=1 が約574KB、jan-codes が約765KB。さらに件数が増える場合は jan-codes もページング化する。
回数終了時の送信渋滞 Handyは未送信入力をローカル保存し、回数終了時に数量入力があった明細のみ送る。大量入力時は500件単位で分割送信し、途中失敗時は成功分だけ履歴化、未送信分はローカルに残す。
履歴表示 Androidの履歴タブは端末内の dirtyInputs / sentHistory のみを表示する。サーバの GET /api/wms/inventory-count-items/{itemId}/logs はログイン中picker本人のHANDYログだけを返す。他人のHANDY履歴とWEB修正履歴は返さない。
WMS bulk count API request_uuid は入力ログで一意制御されるため、通信リトライの二重登録を防止できる。Handyはローカル入力ごとに固定の request_uuid を保持し、再送時も同じ値を使う。サーバ側は加算処理時も差異計算に加算後数量を使う。
確定時の実棚変更キュー作成 差異明細を棚番先頭2桁で分割して inventory_adjustment_queue を作成する。ローカル棚卸 id=8 では3000件の差異が50キューに分割され、最大bucketは381件。確定処理は約9.65秒。数万件規模ではキュー作成時の get() とJSON組み立てがメモリ負荷になるため、次の改善はchunk処理化。
ai-core queue処理 request_id = wms-inventory-adjustment-{count_id}-{bucket} で重複伝票作成を防ぐ。進捗はWMS棚卸の単一queueカラムではなく、inventory_adjustment_queue の該当 request_id 群を集計して表示する。
非在庫管理商品 source_type = WMS_INVENTORY_COUNT の実棚変更では items.is_managed_stock = 0 でも反映対象。通常の手動実棚変更では従来通り対象外。
